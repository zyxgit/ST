## 当前状态

仓库内微服务已具备模块化拆分，**正式租户模型以产品决策为准**。本文档定义 **演进预留**，避免后续大规模重构。

## 数据隔离策略

| 模式 | 适用 | ST 演进备注 |
|------|------|-------------|
| 共享库 + TenantId | 中小 SaaS、成本低 | 所有业务表增加 `tenant_id`（ULID/GUID）；唯一索引含 `tenant_id` |
| 每租户独立 Schema | 合规要求高 | PostgreSQL schema per tenant，迁移成本高 |
| 每租户独立库 | 超大客户 | 运维与连接池复杂 |

**推荐默认**：共享库 + **TenantId** + RLS（可选，PostgreSQL）。

## API 与 JWT

- 租户标识来源优先级（建议）：**JWT Claim**（如 `tid`） > **请求头**（如 `X-Tenant-Id`，仅内部可信网络） > 子域名映射。
- 网关层（`ST.Gateway`）可做租户路由前置校验。

示例 Claim 设计（未来落地时）：

```json
{
  "tid": "018f9e3b-7c2a-7e5f-a7b2-7f8e9d0c1a2b"
}
```

## 推荐方案

- EF Core：全局查询过滤器 `HasQueryFilter` 按 `TenantId` 过滤（引入前需评审性能）。
- 缓存键：`st:t:{tenantId}:...`（见 [`Cache.md`](./Cache.md)）。

## 禁止事项

- 禁止 **客户端任意指定租户 ID** 且无服务端校验（越权风险）。
- 禁止在无租户隔离审计前把 **演示库数据** 直接用于多租户生产。

## AI 注意事项

- AI 生成 CRUD 时，若需求含“租户”，必须在 **实体 + DTO + 查询** 三层同时体现 `TenantId`，不能只改 Controller。
- 不在未确认模型前自动生成 **RLS** SQL——需 DBA 评审。
